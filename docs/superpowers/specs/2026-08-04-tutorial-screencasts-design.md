# Tutorial Screencast Series — Design

**Date:** 2026-08-04
**Status:** Approved, not yet implemented

## Purpose

Produce a growing series of short screencasts that teach **new data-entry staff**
how to perform day-to-day tasks in Full Circle. Each lesson covers exactly one
task, runs 2–4 minutes, and is generated by driving the real application in a
headless browser rather than by hand-recording a desktop.

Lesson 1 is "Key a sales invoice". It was chosen deliberately: it exercises the
hardest parts of the UI (Tribute autocomplete, repeating detail lines, LiveView
form patches, save + document numbering), so a pipeline that handles it will
handle most later lessons.

## Decisions

| Decision | Choice | Reason |
|---|---|---|
| Audience | New staff / data-entry users | Task-oriented, short, in the flow of work |
| Narration | Burned-in on-screen captions, no audio | No TTS dependency, works in a noisy office, trivially re-editable |
| Language | English only | Matches default UI locale; captions stay plain strings if zh is wanted later |
| Data source | Existing `full_circle_dev` | User's choice — see Privacy below |
| Delivery | MP4 files + generated HTML index | No app changes, no hosting decisions, works from a shared drive |
| Recording approach | Live browser recording with captions injected into the page | Only approach that shows the app actually behaving |

### Privacy constraint

`CLAUDE.md` documents `scripts/restore_backup.sh` as restoring **production**
`pg_dump` archives into `full_circle_dev`. Recordings will therefore show real
contact, employee, and payroll data. These videos are for internal staff who
already have access to that data. **Do not publish them externally** — no
YouTube, no public web host, no customer-facing distribution.

### Rejected alternatives

- **Captions added in post with ffmpeg `drawtext`.** Would allow re-wording
  without re-recording, but requires maintaining frame-accurate timestamps by
  hand, and every re-record shifts them.
- **Screenshot slideshow.** Bulletproof and tiny, but has no typing, no dropdown
  opening, no motion. For teaching data entry, watching a field get filled *is*
  the lesson.
- **Offline/cloud TTS voiceover.** Adds a dependency and a speech-to-action
  timing problem for no benefit to the chosen audience.
- **In-app Help LiveView route.** Best discoverability, but adds app code, bloats
  the Docker image with video files, and couples tutorials to deploys.

## Architecture

New top-level `screencasts/` directory, deliberately outside `assets/` so
esbuild and the existing asset pipeline never touch it.

```
screencasts/
  package.json           # playwright only
  config.mjs             # base URL, viewport, credentials from env
  director.mjs           # shared library — all the hard parts
  lessons/
    01-key-a-sales-invoice.mjs
  manifest.json          # id, title, description, order
  record.mjs             # CLI entry point
  build-index.mjs
  templates/index.html
docs/screencasts/        # output: NN-<slug>.mp4 + index.html
```

### Pipeline

1. `record.mjs` launches a Playwright Chromium context with
   `recordVideo: { dir, size: { width: 1280, height: 720 } }` and a matching
   1280×720 viewport. 720p is readable for text-dense ERP forms at a modest
   file size.
2. The named lesson module runs against the dev server at `http://localhost:4000`.
3. Playwright writes a `.webm`.
4. ffmpeg transcodes to H.264 mp4
   (`-c:v libx264 -crf 23 -preset slow -pix_fmt yuv420p`) into `docs/screencasts/`.

Chromium is installed on demand with `npx playwright install chromium`. No Xvfb
is required — headless Playwright records without a display server, which also
sidesteps this machine's Wayland session.

### Lesson module contract

A lesson is an ES module exporting a single `async function run(d)` where `d` is
the director. It is declarative and short:

```js
export async function run(d) {
  await d.title("Lesson 1 — Keying a Sales Invoice");
  await d.login();
  await d.say("Open Billing and start a new sales invoice");
  await d.click('a[href$="/Invoice/new"]');
  await d.say("Type the customer's name and pick from the list");
  await d.pickAutocomplete('#invoice_contact_name', 'Ah Seng');
  // …
}
```

Everything difficult lives in `director.mjs` and is written once. A lesson file
should read like a lesson plan, not like browser automation.

The selectors shown above are **illustrative only**. Actual selectors must be
read off `InvoiceLive.Form` and its detail component during implementation, not
assumed from this document.

## `director.mjs` — the five hard problems

**1. There is no mouse cursor.** Playwright's video recorder does not draw a
pointer, so an unmodified recording shows form fields filling themselves.
`page.addInitScript()` injects a styled cursor element on every navigation.
`click()` and `hover()` tween it to the target element's centre over ~400ms
using `requestAnimationFrame`, then perform the real Playwright action.

**2. Captions.** A fixed bottom bar, injected by the same init script.
`say(text)` sets its content and holds for a computed reading time:
`max(2000, 800 + 400 × wordCount)` ms.

**3. Highlights.** `highlight(selector)` positions a ring element over the
target's bounding box and fades it out, drawing the eye to the field under
discussion.

**4. LiveView settling.** After every action, wait until no
`.phx-change-loading`, `.phx-submit-loading`, or `.phx-click-loading` classes
remain in the document. This is materially more reliable than fixed sleeps and
is the mechanism the whole director depends on for pacing.

**5. Tribute autocomplete.** `assets/js/tri_autocomplete.js` constructs Tribute
with `autocompleteMode: true`, meaning it reacts to real keystrokes and renders
its menu into a `.tribute-container` element appended to `<body>`.
Playwright's `fill()` sets a value without dispatching key events and would
never open the menu. `pickAutocomplete(sel, text)` therefore:

1. focuses the field,
2. `pressSequentially(text, { delay: 90 })`,
3. waits for `.tribute-container li` to be visible,
4. clicks the item matching `text`, falling back to the first item.

Note that `cacheSearch` caches contact/account/good/employee/house lookups in
browser storage, so the first run of a lesson performs a remote fetch and later
runs may hit cache. Timing differs slightly between runs; the LiveView-settling
wait absorbs this.

**Title and end cards** are injected full-screen overlays held ~2.5s, not
separate video files. This keeps the entire lesson in one recording and avoids
an ffmpeg concat step.

### Credentials

Read from `SCREENCAST_EMAIL` and `SCREENCAST_PASSWORD` environment variables.
Never committed. `record.mjs` fails fast with a clear message if either is unset.

## Lesson 1 beat sheet

Target runtime ~3 minutes.

1. Title card — "Lesson 1 — Keying a Sales Invoice"
2. Log in (email, password, submit)
3. Select the active company
4. Navigate Billing → Invoice → New
5. Set the invoice date
6. Customer via `pickAutocomplete`
7. Line 1: good via `pickAutocomplete`, quantity, unit price — highlight the
   computed line total
8. Line 2, to demonstrate that lines repeat
9. Save; highlight the flash message and the assigned invoice number
10. Open the print view briefly
11. End card

### Document creation

The script performs a **real save**. Seeing the document number get assigned is
the payoff of the lesson, and a form that never submits teaches a clerk nothing.

Consequences, accepted:

- Each take consumes one gapless invoice number in `full_circle_dev`.
- Re-recording produces a different number each time.

Mitigation: the script appends every created document number to
`screencasts/.created.log` (gitignored) so the junk records can be deleted
manually later.

## Output and index

`build-index.mjs` reads `manifest.json` and emits a self-contained
`docs/screencasts/index.html`:

- No external assets or CDN references, so it works over `file://` from a shared
  drive or USB stick.
- One `<video>` element per lesson with title and description.
- Styled for both light and dark themes.

### Version control

**Committed:** all scripts, `manifest.json`, `templates/index.html`, generated
`index.html`.

**Gitignored:** `docs/screencasts/*.mp4` and `screencasts/.created.log`. A
3-minute 720p capture is 5–15MB and is fully reproducible from the scripts;
committing videos would bloat the repository permanently for no gain.
Distribution is by copying the folder, not through git.

## Maintenance

The chief long-term risk is that a LiveView change silently breaks a recording
script and nobody notices for months.

`node record.mjs --all --dry` runs every lesson headless with no video recording
and no ffmpeg pass — pure selector verification, a few seconds per lesson. Run it
after touching Billing LiveViews to learn immediately which lessons need
re-recording.

## Verification

Before the work is called complete:

1. `node record.mjs 01 --dry` passes — every selector resolves.
2. A real recording produces a playable mp4 of roughly the expected duration.
3. Frames extracted with ffmpeg are **visually inspected**: captions not clipped
   at the edges, cursor visible and landing on the right targets, form text
   legible at 720p.
4. `docs/screencasts/index.html` opens over `file://` and plays the video in
   both light and dark themes.

## Growing the series

Adding lesson N is one new file in `lessons/` plus one entry in `manifest.json`.
No change to the director unless the lesson needs a genuinely new interaction
primitive, in which case the primitive is added to the director rather than
inlined into the lesson.

Likely lesson 2+ candidates, in rough order of daily volume: recording a receipt
against outstanding invoices, entering a purchase invoice, searching and printing
an existing document, the egg stock day board.

## Out of scope

Explicitly not built:

- Text-to-speech narration of any kind
- Chinese captions (captions remain plain strings in the lesson file, so this
  stays cheap to add later)
- An in-app Help route serving the videos
- Any hosting, upload, or streaming
- A dedicated seeded screencast database
